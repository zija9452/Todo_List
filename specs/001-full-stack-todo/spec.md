## User Scenarios & Testing *(mandatory)*

### User Story 1 - User Creates and Manages Personal Tasks (Priority: P1)

As a registered user, I want to securely create, view, update, and delete my personal tasks so that I can manage my daily activities effectively without other users seeing my data.

**Why this priority**: This represents the core functionality of the todo application and enables the fundamental value proposition of the application.

**Independent Test**: Can be fully tested by signing in as a user, creating tasks, viewing them, modifying them, and deleting them - delivers the essential value of a todo app with proper user isolation.

**Acceptance Scenarios**:

1. **Given** I am a logged-in user, **When** I create a new task with a title and optional description, **Then** the task appears in my personal task list with appropriate ownership and I can see it on subsequent visits
2. **Given** I have tasks in my personal list, **When** I access my tasks endpoint, **Then** I see only my tasks and not others' tasks
3. **Given** I am logged in with a JWT token, **When** I attempt to access another user's tasks, **Then** I receive a 403 Forbidden error
4. **Given** I have a task with a specific ID, **When** I update its details or completion status, **Then** only that specific task is modified and the changes are persisted
5. **Given** I have completed a task, **When** I mark it as completed, **Then** its status updates in the system and it appears differently in my list

---

### User Story 2 - User Authenticates and Maintains Session (Priority: P2)

As a user, I want to register for an account and securely log in to maintain my tasks across sessions using JWT authentication.

**Why this priority**: Authentication is foundational to the multi-user model and enables proper data isolation.

**Independent Test**: Can be tested by registering a new user, logging in, and verifying that a secure JWT session is established and maintained.

**Acceptance Scenarios**:

1. **Given** I am a new user, **When** I visit the registration page, **Then** I can create an account with proper authentication
2. **Given** I am logged in with valid credentials, **When** I make API requests, **Then** my JWT token is properly validated and my identity verified
3. **Given** I have a valid session, **When** my JWT token expires, **Then** I am redirected to login or prompted to re-authenticate
4. **Given** I attempt to access protected resources without a valid JWT token, **Then** I receive a 401 Unauthorized error

---

### User Story 3 - User Sorts and Filters Tasks (Priority: P3)

As a user, I want to sort and filter my tasks by various criteria so that I can efficiently find and manage my tasks.

**Why this priority**: This enhances usability and makes the application more practical for users managing multiple tasks.

**Independent Test**: Can be tested by having a user with multiple tasks and verifying that sorting and filtering operations return the expected results.

**Acceptance Scenarios**:

1. **Given** I have multiple tasks in my list, **When** I filter by status (pending/completed/all), **Then** only tasks matching the status are displayed
2. **Given** I have multiple tasks, **When** I sort by creation date, title, or due date, **Then** tasks are displayed in the requested order
3. **Given** I have tasks with different priorities, **When** I filter by priority, **Then** only tasks matching the selected priority are displayed

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide JWT-based authentication using Better Auth for secure user identification and session management
- **FR-002**: System MUST validate JWT tokens against BETTER_AUTH_SECRET and enforce user ownership checks for all API requests
- **FR-003**: System MUST expose REST API endpoints: GET/POST/PUT/DELETE /api/{user_id}/tasks and PATCH /api/{user_id}/tasks/{id}/complete
- **FR-004**: System MUST require Authorization: Bearer <token> header on all API requests with appropriate error responses (401, 403, 404, 422)
- **FR-005**: System MUST persist tasks in a PostgreSQL database using SQLModel ORM with proper relationships and indexing
- **FR-006**: System MUST enforce data validation for tasks including title length (1-200 characters), description length (<=1000 characters), and proper date formats
- **FR-007**: Users MUST be able to create tasks with title (required), description (optional), priority (high/medium/low/null), due date (optional), and completion status
- **FR-008**: System MUST support query parameters for filtering and sorting: ?status=all|pending|completed, ?sort=created|title|due_date, ?order=asc|desc
- **FR-009**: System MUST ensure that users can only access their own tasks (enforcing user_id in URL === user_id from JWT token)
- **FR-010**: Frontend MUST integrate with Better Auth for user session management and attach JWT tokens to API requests
- **FR-011**: System MUST support task priority levels as enum: high, medium, low, or null
- **FR-012**: System MUST provide proper timestamps for task creation and updates (created_at, updated_at)
- **FR-013**: System MUST maintain data persistence across application restarts with 99.9% reliability

### Key Entities *(include if feature involves data)*

- **Task**: Represents a user's to-do item with attributes: id (unique identifier), user_id (foreign key linking to user), title (1-200 characters), description (up to 1000 characters, optional), completed (boolean), priority (enum of high/medium/low/null), due_date (date, optional), created_at (timestamp), updated_at (timestamp). Related to User entity via user_id foreign key.
- **User**: Represents an authenticated user of the system who owns tasks, identified by a unique user identifier from Better Auth. Each user has a collection of associated tasks accessible only to them.
- **Authentication Token**: Represents a JWT token issued by Better Auth, containing user identity claims that are verified by the backend to ensure proper authorization.
